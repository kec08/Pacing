## 구현 요약

러닝 탭의 같이 듣기에서 호스트가 곡을 변경했을 때, 게스트가 같은 곡 전환을 여러 번 준비하거나 큰 앨범 커버 데이터를 반복 전송하면서 발생할 수 있던 지연·끊김 요인을 제거했다.

호스트는 현재 재생 곡 변경을 감지하면 즉시 새 재생 이벤트를 발행한다. 게스트는 이 이벤트의 고유 ID를 기준으로 최신 곡 전환을 한 번만 적용하고, 이전 비동기 준비 작업이 늦게 끝나도 새 곡 재생 상태를 덮어쓰지 못하도록 처리했다. 동일 곡의 주기 위치 보정에서는 재생 큐를 다시 만들지 않는다.

## 구현된 기능 목록

- [x] `ListenSession`에 곡 전환 단위의 `playbackEventID` 추가
- [x] 호스트의 현재 곡 변경 시 재생 이벤트 즉시 발행
- [x] 1초 주기 브로드캐스트는 동일 이벤트 ID를 유지해 위치·재생 상태 보정으로만 사용
- [x] 게스트의 동일 이벤트 중복 `setQueue`·`prepareToPlay()` 실행 차단
- [x] 새 이벤트가 도착했을 때 이전 비동기 준비 작업 결과 무효화
- [x] 현재 곡이 같은 경우 큐 재설정 없이 임계값 기반 위치 보정 유지
- [x] Store ID 우선 재생 및 제목 기반 fallback 유지
- [x] 앨범 커버 JPEG Base64 변환·Realtime Database 전송을 곡 전환 시에만 수행
- [x] Apple Music 현재 곡 변경 알림에서 즉시 세션 브로드캐스트

## 계획서 대비 변경 사항

| 항목 | 계획 | 실제 구현 | 사유 |
|------|------|-----------|------|
| 전환 이벤트 모델 | 별도 재생 이벤트 경로 분리 검토 | 기존 `listenSessions/{sessionID}`에 `playbackEventID`를 추가 | Firebase 스키마 변경 범위를 최소화하면서 이벤트·위치 보정을 구분할 수 있음 |
| 중복 동기화 방지 | 최신 이벤트만 처리 | 진행 중 이벤트 ID와 동기화 토큰으로 이전 비동기 작업 결과 무효화 | `prepareToPlay()`가 오래 걸려도 새 곡 재생을 방해하지 않도록 보강 |
| 앨범 이미지 처리 | 네트워크 비용 축소 | 곡 전환 시에만 Base64 변환·전송 | 매초 이미지 인코딩·대용량 페이로드 전송을 제거 |
| 자동 테스트 | 순수 동기화 판단 로직의 단위 테스트 분리 | 기존 테스트 타깃의 빌드·실행 회귀 검증 수행 | 현재 동기화 로직이 시스템 플레이어·Firebase와 결합되어 있어 Apple Music 재생 자체는 실기기 QA가 필요 |

## 알려진 제한사항

- Apple Music의 새 곡 다운로드·스트리밍 버퍼링 시간은 앱 코드가 완전히 제어할 수 없다. 이번 변경은 앱 내부 중복 동기화·반복 이미지 전송으로 인한 추가 지연을 제거하는 범위다.
- 서로 다른 Apple Music 계정의 두 실기기에서 호스트·게스트 재생을 동시에 검증하지 못했다. 따라서 실제 무음 시간이 0초라고 확정할 수는 없다.
- 현재 자동화 테스트는 기본 단위/UI 실행 테스트다. 시스템 플레이어 재생과 Firebase 실시간 전송은 시뮬레이터에서 유효하게 재현되지 않는다.
- 기존 워크트리의 `Pacing/Pacing.xcodeproj/project.pbxproj` 변경은 이번 기능과 무관하며 커밋에 포함하지 않았다.
