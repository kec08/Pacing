# feat #42 전체 로딩 및 음악 탭 성능 최적화 계획서

> **상태**: 검토 대기
> **작성일**: 2026-07-15
> **관련 이슈**: 미정
> **브랜치**: `feat/42-performance-optimization`

## 1. 목적 및 배경

현재 앱은 각 탭 진입 시 필요한 데이터를 즉시 조회하는 구조가 많아 초기 체감 속도가 느립니다.
특히 노래 탭은 진입 시점에 Apple Music 권한 확인, 추천 데이터 조회, 내 플레이리스트 동기화, 친구 플레이리스트 재조회가 한 번에 묶여 있어 첫 화면 응답성이 떨어집니다.

이번 작업의 목적은 다음 두 가지입니다.

- 탭 전환 시 사용자가 먼저 화면을 볼 수 있도록 초기 응답성을 개선한다.
- 실제로 다시 불러올 필요가 없는 데이터는 재사용하고, 비싼 네트워크/동기화 작업은 분리한다.
- 노래 탭에서는 `최근에 들은 앨범`만 실시간성 있게 반영하고, 나머지 섹션은 캐시 우선 전략으로 전환한다.

## 2. 사용자 시나리오

```text
사용자가 홈, 친구, 노래, 마이 탭을 오갈 때
→ 이미 본 데이터는 즉시 표시되고
→ 필요한 경우에만 백그라운드 갱신이 일어나며
→ 화면 전체가 매번 다시 로딩되는 느낌 없이 자연스럽게 탐색할 수 있다

사용자가 노래 탭에 진입하면
→ 상단과 주요 섹션이 먼저 빠르게 보이고
→ 최근에 들은 앨범은 탭 재진입 시 최신 재생 이력 기준으로 우선 갱신되며
→ 친구 플레이리스트/추천 데이터는 캐시 또는 지연 갱신으로 보강되고
→ 내 플레이리스트 동기화는 탭 진입마다 강제 실행되지 않는다
```

## 3. 화면 구성

### 주요 화면
- `MainTabView`: 탭 생명주기 및 초기 preload 전략 검토 대상
- `SongView`: 현재 가장 큰 체감 병목 구간
- `HomeView`: 홈 데이터 새로고침 정책 정리 대상
- `FriendsView`: 친구/추천 친구 조회 구조 최적화 대상
- `MyView`: 프로필/러닝 기록 재조회 시점 정리 대상

### UI 요소
- 탭 첫 화면: 즉시 노출 가능한 캐시 데이터 우선 표시
- 스켈레톤 UI: 최초 진입에만 제한적으로 노출
- 당겨서 새로고침: 강제 갱신 진입점으로 유지
- 노래 탭 동기화 버튼: 무거운 라이브러리 동기화를 명시적 사용자 액션으로 분리
- 최근에 들은 앨범 섹션: 실시간 반영 우선 대상

## 4. 데이터 흐름

### 사용 데이터
- Firestore 컬렉션:
  - `users/{uid}/runHistory`
  - `users/{uid}/friends`
  - `friendRequests`
  - `sharedPlaylists`
- Realtime DB 경로:
  - `listenSessions`
  - `activeRunners`
- MusicKit API:
  - `MusicRecentlyPlayedRequest`
  - `MusicPersonalRecommendationsRequest`
  - `MusicCatalogChartsRequest`
  - `MusicCatalogSearchRequest`
  - `MusicLibraryRequest`

### 현재 확인된 병목
- `SongViewModel.load()`
  - 탭 진입 시 추천 조회와 친구 플레이리스트 조회뿐 아니라 `syncCurrentUserPlaylists()`까지 함께 실행
  - `최근에 들은 앨범`과 캐시 가능한 추천 데이터가 같은 진입점에 묶여 있음
- `AppleMusicRecommendationService.syncCurrentUserPlaylists()`
  - 플레이리스트별 트랙 로드와 Firestore 저장이 순차 실행
- `AppleMusicRecommendationService.fetchGenreAlbumRows()` / `fetchMoodPlaylists()`
  - 장르/무드별 검색 요청이 순차 실행
- `FirestoreService.fetchFriendSharedPlaylists()`
  - `fetchFriends()` 호출 후 친구별 플레이리스트를 다시 개별 조회하는 N+1 구조
- `FirestoreService.fetchFriends()`
  - 친구별 마지막 러닝 날짜를 개별 조회
- `HomeView`, `FriendsView`, `MyView`
  - 탭별 최초 로드 정책은 있으나 캐시 유효 시간과 재사용 전략이 없음

### 목표 상태 관리 방향
- `View`
  - 최초 표시와 수동 새로고침만 트리거하고 비즈니스 로직 최소화
- `ViewModel`
  - `initialLoad`, `refresh`, `backgroundRefresh`, `shouldReload` 역할 분리
- 캐시 정책
  - 메모리 캐시 + 마지막 갱신 시각 기반 soft refresh
  - 단, `최근에 들은 앨범`은 캐시 우선이 아니라 재진입 시 최신값 재조회 우선
- 로딩 상태
  - 전체 `isLoading`보다 섹션 단위 로딩 유지

## 5. 작업 목록 (Tasks)

- [ ] Task 1. 성능 병목 계측 및 로딩 정책 정리
  - 노래/홈/친구/마이 탭의 초기 로드, 재진입, 당겨서 새로고침 시나리오 분리
  - 각 ViewModel의 네트워크 호출 타이밍과 중복 호출 여부 점검
  - 사용자 체감 기준으로 즉시 표시 데이터와 지연 허용 데이터를 분류

- [ ] Task 2. 노래 탭 로딩 구조 분해
  - `SongViewModel.load()`를 `initialLoad`, `refresh`, `refreshRecentlyPlayedAlbums`, `syncLibraryIfNeeded` 등으로 분리
  - 탭 진입 시 자동 라이브러리 동기화를 제거하거나 조건부 실행으로 축소
  - `최근에 들은 앨범`은 탭 재진입 시 우선 갱신하고, 친구 플레이리스트/추천 플레이리스트/장르/무드 섹션은 캐시 우선 구조로 정리
  - 마지막 로드 시각을 두고 추천성 데이터는 일정 시간 내 재진입 시 캐시 우선 노출

- [ ] Task 3. 음악 데이터 조회 비용 절감
  - 장르/무드 검색 요청 병렬화 검토
  - 공유 플레이리스트 동기화 저장량과 호출 빈도 축소
  - artwork prefetch 시점과 범위 재검토
  - 최근에 들은 앨범을 제외한 추천 데이터를 메모리 캐시로 재사용

- [ ] Task 4. Firestore 조회 구조 최적화
  - 친구 목록과 친구 플레이리스트 조회의 N+1 패턴 완화
  - 마지막 러닝 상태 계산을 저장 데이터 기반으로 대체할지 검토
  - 친구 탭/노래 탭 공용 데이터 재사용 구조 검토

- [ ] Task 5. 탭 공통 캐시 및 preload 전략 적용
  - `MainTabView` 또는 상위 계층에서 preload 가능한 데이터 선별
  - 홈/친구/마이 탭의 첫 표시 속도 개선을 위한 캐시 정책 도입
  - 불필요한 전체 스켈레톤 재노출 방지

- [ ] Task 6. QA 및 회귀 검증
  - 탭 전환 반복 시 로딩 체감 비교
  - 노래 탭 첫 진입/재진입/새로고침 시나리오 점검
  - 최근에 들은 앨범이 실제 재생 후 재진입 시 최신 순서로 반영되는지 확인
  - Apple Music 권한 없음 / 권한 허용 / 구독 불가 상태 점검
  - 친구 데이터 없음 / shared playlist 없음 / 러닝 기록 없음 상태 점검

## 6. 완료 기준 (Acceptance Criteria)

- [ ] 노래 탭 재진입 시 전체 로딩이 반복되지 않고, 기존 데이터가 우선 노출된다
- [ ] 노래 탭 재진입 시 `최근에 들은 앨범`만 최신 재생 이력 기준으로 다시 반영된다
- [ ] 노래 탭 진입마다 내 플레이리스트 동기화가 자동으로 실행되지 않는다
- [ ] 친구 플레이리스트/추천/최근 앨범 섹션이 전체 화면 블로킹 없이 부분 갱신된다
- [ ] 친구 플레이리스트/추천/장르/무드 섹션은 불필요한 실시간 재조회 없이 캐시 또는 명시적 갱신 기준으로 동작한다
- [ ] 홈/친구/마이 탭도 첫 진입 이후에는 불필요한 재로딩 체감이 줄어든다
- [ ] 당겨서 새로고침 시에만 명시적 강제 갱신이 수행된다
- [ ] 기능 회귀 없이 기존 빈 상태, 에러 상태, 권한 상태가 유지된다

## 8. 특이 사항 / 기술 검토

- 현재 `TabView` 구조상 탭 View 인스턴스는 유지될 가능성이 높지만, 사용자가 느끼는 지연은 "탭에 들어갈 때마다 다시 뜨는 스켈레톤"만의 문제가 아니라 첫 진입 시 작업량 자체가 과한 영향이 큽니다.
- 특히 노래 탭은 `load()` 안에서 권한 확인, 추천 조회, 친구 플레이리스트 조회, 내 플레이리스트 동기화가 함께 실행되고 있어 UX 기준 우선순위 재분리가 필요합니다.
- 이번 요구사항 기준으로 실시간 반영 우선순위는 `최근에 들은 앨범`만 부여하고, 나머지 추천성 데이터는 캐시 우선으로 분리하는 것이 가장 효과적입니다.
- `fetchFriendSharedPlaylists()`는 친구 목록 조회 후 친구별 playlist query를 추가로 수행하고 있어 친구 수가 늘수록 체감 지연이 커질 수 있습니다.
- `fetchFriends()`도 친구별 마지막 러닝 조회를 추가 수행하므로 친구 탭과 노래 탭 모두에 간접 비용을 발생시킵니다.
- 이번 작업에서는 무분별한 리팩토링보다, 요청 범위에 맞는 캐시 계층과 로딩 트리거 정리에 집중하는 것이 적절합니다.
- 실제 개선 효과 확인을 위해 Xcode Instruments 또는 로그 기반 측정 포인트를 일부 추가하는 방안을 검토합니다.
