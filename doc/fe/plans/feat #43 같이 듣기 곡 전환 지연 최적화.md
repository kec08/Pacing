## 1. 목적 및 배경

러닝 탭의 같이 듣기에서 호스트가 다음 곡으로 넘기면 게스트 기기에서 약 5초간 무음 또는 끊김이 발생한다. 현재 호스트는 매초 전체 세션을 갱신하고, 게스트는 세션 값 변경마다 재생 상태를 판정한다. 곡 ID가 달라지면 `setQueue`와 `prepareToPlay()`를 다시 수행하므로, 곡 전환 이벤트와 일반 위치 보정 이벤트가 섞일 경우 불필요한 재동기화·중복 준비가 발생할 수 있다.

이번 작업은 **곡 전환 이벤트를 식별 가능한 단일 명령으로 전달**하고, 게스트가 최신 곡 전환만 처리하도록 변경한다. 이미 같은 곡을 듣는 중에는 큐를 다시 구성하지 않고 위치·재생 상태만 가볍게 보정한다. 목표는 네트워크 수신 후 재생 명령을 즉시 시작하고, 중복 동기화로 생기는 추가 공백을 제거하는 것이다.

## 2. 사용자 시나리오

```
호스트가 러닝 중 다음 곡 버튼을 누른다
→ 호스트의 새 곡 ID와 전환 시각이 Realtime Database에 즉시 기록된다
→ 게스트는 새 전환 식별자를 감지하고 이전 동기화 작업을 무시한다
→ 게스트는 새 곡 ID로 큐를 설정하고 준비 완료 즉시 보정된 위치에서 재생한다
→ 이후 매초 위치 갱신은 같은 곡의 위치 차이가 허용 범위를 초과할 때만 보정한다
```

## 3. 화면 구성

### 주요 화면
- 러닝 화면의 음악 카드: 기존 곡 정보·다음 곡 조작을 유지한다.
- 같이 듣기 시트: 기존 연결/종료 UI를 유지한다.

### 상태 피드백
- 곡 전환 동기화 중에는 기존 곡 정보가 유지되며, 게스트 재생이 실패한 경우에만 사용자에게 재시도 가능한 상태를 제공할지 구현 단계에서 기존 UX와 함께 검토한다.
- 화면 구조 변경은 최소화하고, 접근성 라벨과 터치 영역에는 영향을 주지 않는다.

## 4. 데이터 흐름

### 사용 데이터
- Realtime Database:
  - `listenSessions/{sessionID}`: 세션 상태 및 재생 스냅샷
  - `listenSessions/{sessionID}/playback`: 곡 전환 식별자, 곡 Store ID, 위치, 재생 상태, 서버 시각을 가진 재생 명령 경로로 분리 검토
- MediaPlayer / MusicKit:
  - `MPMusicPlayerController.systemMusicPlayer`
  - `setQueue(with:)`, `prepareToPlay()`, `currentPlaybackTime`, 재생 상태·현재 곡 변경 알림

### 상태 관리
- `ListenTogetherViewModel`
  - 호스트: 현재 곡 변경 시 즉시 전환 이벤트 발행, 주기 브로드캐스트는 위치 보정 전용으로 제한
  - 게스트: 마지막 처리 전환 식별자, 진행 중 동기화 작업, 최신 세션 스냅샷을 관리
  - 게스트가 이미 같은 Store ID를 재생 중이면 큐 재설정 없이 임계값 기반 위치 보정만 수행
- `RealtimeDBService`
  - 전체 세션 `.value` 구독 대신 재생 데이터의 변경 범위를 좁히고, 곡 전환과 위치 갱신을 구분할 수 있도록 API를 정리

## 5. 작업 목록 (Tasks)

- [ ] Task 1: 호스트 곡 변경부터 게스트 `prepareToPlay()` 호출까지의 시간·호출 횟수를 로그로 측정하고 지연 구간을 확정
- [ ] Task 2: 재생 데이터에 단조 증가하는 전환 식별자와 서버 기준 전환 시각을 추가하고, 호스트 곡 변경 알림에서 즉시 발행
- [ ] Task 3: Realtime Database 쓰기·구독을 곡 전환 명령과 주기 위치 보정으로 분리하여 전체 세션 갱신 및 불필요한 관찰 콜백을 축소
- [ ] Task 4: 게스트에 최신 전환 식별자만 적용하는 취소/중복 방지 로직을 추가하고, 이미 같은 곡이면 큐 재설정을 하지 않도록 수정
- [ ] Task 5: Store ID 우선 큐 설정과 제목/아티스트 fallback을 유지하되, 실패·재시도·세션 종료 시 진행 중 작업이 재생을 되돌리지 않도록 보강
- [ ] Task 6: 서버 시각과 수신 시각으로 목표 재생 위치를 보정하고, 허용 오차 이내의 주기 업데이트는 무시
- [ ] Task 7: 단위 테스트 가능한 순수 동기화 판단 로직을 분리하고, 빌드 및 2대 실기기 QA를 수행

## 6. 완료 기준 (Acceptance Criteria)

- [ ] 호스트의 곡 변경이 1회 발생하면 게스트의 큐 설정·준비 작업도 최신 곡에 대해 최대 1회만 실행된다.
- [ ] 이전 곡의 비동기 준비가 늦게 끝나도 새 곡 재생 상태를 덮어쓰지 않는다.
- [ ] 같은 곡의 주기적 위치 갱신은 오차가 임계값 이내일 때 `setQueue` 또는 `prepareToPlay()`를 호출하지 않는다.
- [ ] 새 곡 Store ID가 전달되는 경우 제목 검색 없이 해당 ID로 재생을 시도한다.
- [ ] Store ID 기반 재생 실패 시 기존 제목/아티스트 fallback이 동작하며, 실패 원인이 로그로 확인된다.
- [ ] 두 대의 실기기에서 10회 이상 연속 곡 넘김을 수행해 게스트 무음/끊김, 전환 지연, 현재 곡 불일치를 기록한다.
- [ ] 네트워크 상태가 달라져도 게스트가 최신 전환 이벤트만 추종하며 세션이 종료되지 않는다.
- [ ] 프로젝트 빌드와 관련 테스트가 성공한다.

## 8. 특이 사항 / 기술 검토

- Apple Music 스트리밍의 실제 버퍼링 시간은 앱이 완전히 제거할 수 없다. 본 작업은 앱 내부의 중복 `setQueue`/`prepareToPlay()`와 늦게 완료된 비동기 작업으로 인한 추가 지연을 제거하는 범위다.
- Firebase의 `ServerValue.timestamp()`는 서버 반영 뒤 확정되므로, 호스트 발행 시각과 수신 시각을 구분해 위치 보정 오차를 점검한다.
- `MPMusicPlayerController`는 기기 전역 시스템 플레이어이므로, 같이 듣기 세션이 종료되거나 새 전환이 도착하면 이전 비동기 작업의 결과를 반드시 무효화해야 한다.
- MusicKit/Apple Music 권한, 구독, 네트워크 캐시 상태에 따라 재생 시작 시간은 달라질 수 있으므로, 시뮬레이터가 아닌 서로 다른 Apple ID의 실기기에서 검증한다.
- 기존에 수정된 `Pacing/Pacing.xcodeproj/project.pbxproj`는 본 작업과 무관한 변경으로 보이며 포함하거나 되돌리지 않는다.
- 계획 검토·승인 후 GitHub 이슈를 생성하고 `dev` 기준으로 `feat/43-listen-together-track-transition` 브랜치를 분기한다.
