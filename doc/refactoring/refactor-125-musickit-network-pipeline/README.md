# MusicKit 네트워크 요청 병목 리팩토링

> 상태: 구현·벤치마크 완료 / 컴파일 QA 통과
> 작성일: 2026-08-22
> 관련 이슈: [#125 MusicKit 네트워크 요청 병목 최적화](https://github.com/kec08/Pacing/issues/125)
> 브랜치: `refactor/125`

## 대상

| 대상 | Before 병목 | 변경 방향 |
| --- | --- | --- |
| 추천 화면 | 최근 재생·장르·무드·개인 추천을 직렬 요청 | 독립 요청을 `async let`로 동시 시작 |
| 공유 플레이리스트 곡 해석 | 25개 제한을 넘는 ID를 한 번에 요청한 뒤 나머지를 검색 fallback | ID를 25개 단위로 나눠 카탈로그 요청 |

## 검증 범위

- 추천 요청 스케줄링은 실제 MusicKit 인증·네트워크 없이 동일 지연을 주는 시뮬레이션으로 비교한다.
- 곡 ID 청크 분할은 요청 수와 결과 ID 집합 동등성을 검증한다.
- 실제 MusicKit 서버 응답 시간은 환경·계정·네트워크에 따라 달라지므로 마이크로벤치마크와 구분해 기록한다.

## 측정 결과

10ms 지연의 독립 요청 10개를 모델링한 릴리스 최적화(`-O`) 시뮬레이션을 세 번 독립 실행했다. 추천 critical path 중앙값은 `144.40425 ms → 57.99058 ms`로 **59.8% 개선**이었다. 실제 MusicKit 네트워크 시간이 아닌 요청 스케줄링 구조의 비교값이다.

100개 곡 ID를 25개 제한으로 처리하는 조건에서는 카탈로그 요청 수가 `76회 → 4회`로 **94.7% 감소**했다. 기존 76회는 최초 카탈로그 요청 1회와 응답에서 빠진 75개 곡의 검색 fallback을 합산한 조건이다.
