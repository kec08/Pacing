# 내 프로필 공개 범위 및 다크 모드 편집 화면 개선 계획서

> **상태**: 개발 진행
> **작성일**: 2026-08-18
> **관련 이슈**: #111
> **브랜치**: `feat/111-profile-visibility-simplification`

---

## 1. 목적 및 배경

내 프로필 화면에서 사용자가 자신의 공개 범위를 직접 선택할 수 있게 한다. 공개 범위는 `전체 공개`, `친구만 공개`, `비공개`의 세 단계이며, 다른 사용자가 내 프로필을 조회할 때 실제 데이터 접근에도 적용한다.

프로필 편집 화면은 다크 모드에서도 배경·입력 필드 대비가 자연스럽게 보이도록 디자인 시스템 색상을 사용한다. 키·몸무게는 러닝 칼로리 계산에 사용하므로 온보딩과 프로필 편집에서 기존과 같이 유지한다.

## 2. 사용자 시나리오

```
내 프로필 화면에서 사용자가 우측 상단 설정 버튼을 누른다
→ "프로필 공개 설정" 화면에서 전체 공개 / 친구만 공개 / 비공개 중 하나를 선택한다
→ 저장하면 설정이 즉시 반영되고, 다른 사용자의 검색·추천·프로필 진입 권한이 새 범위에 맞게 달라진다

사용자가 프로필 편집을 누른다
→ 프로필 사진과 닉네임만 수정한다
→ 라이트/다크 모드 모두에서 읽기 쉬운 입력 화면으로 저장한다

신규 사용자가 회원가입을 완료한다
→ 닉네임, 성별, 키·몸무게, 프로필 사진을 설정하고 앱을 시작한다
```

## 3. 화면 구성 및 UX

### 내 프로필 상세

- 우측 상단: 44pt 이상의 글래스 설정 버튼(`gearshape`)을 추가한다.
- 버튼 탭: `프로필 공개 설정` 화면으로 이동한다.
- 기존 프로필 편집 CTA는 유지한다.

### 프로필 공개 설정

- 선택지: `전체 공개`, `친구만 공개`, `비공개`.
- 각 선택지는 제목·설명·선택 표시를 가진 한 행이며, 탭 영역은 행 전체로 제공한다.
- 저장 중에는 중복 입력을 막고, 성공 시 이전 화면으로 돌아가 최신 상태를 표시한다.
- 설명 기준:
  - 전체 공개: 로그인한 모든 사용자가 검색·추천·프로필 조회 가능
  - 친구만 공개: 상호 친구만 프로필 조회 가능, 비친구 검색·추천에서 제외
  - 비공개: 다른 사용자의 검색·추천·프로필 조회에서 제외

### 프로필 편집 및 온보딩

- 프로필 편집: 프로필 사진, 닉네임, 키·몸무게를 유지한다.
- 다크 모드: 고정 `Color.white` 입력 카드 대신 `Color.backgroundPrimary`, `Color.backgroundSecondary`, `Color.surfaceBorder`, `Color.textPrimary` 토큰을 사용한다.
- 온보딩: 키·몸무게 입력 단계와 체중 기반 칼로리 계산을 유지한다.

## 4. 데이터 및 권한 설계

### Firestore 데이터

`users/{uid}`에 다음 필드를 추가한다.

```text
profileVisibility: "public" | "friendsOnly" | "private"
profileVisibilityUpdatedAt: serverTimestamp
```

- 기존 사용자에서 필드가 없는 경우 `public`으로 해석해 현재 공개 동작을 보존한다.
- 키·몸무게는 기존대로 저장하며, 더 이상 수집하지 않는 `age` 필드만 신규 저장 시 정리한다.

### 조회 권한과 검색

- 본인 조회는 항상 허용한다.
- 다른 사용자 조회는 공개 범위와 상호 친구 여부를 함께 검증한다.
- 현재 `users` 컬렉션을 클라이언트가 직접 조회하는 검색·추천은 비공개/친구만 공개 문서를 안전하게 필터링할 수 없다. Firestore 규칙은 쿼리 결과를 후처리 필터로 사용하지 않기 때문이다.
- 따라서 검색·추천과 다른 사용자 프로필 조회는 인증된 Callable Function(또는 동등한 서버 측 Repository)을 통해 공개 범위와 상호 친구 관계를 판별한 뒤 허용된 최소 프로필 데이터만 반환하도록 전환한다.
- `runHistory`, `recentSongs`는 현재의 상호 친구 전용 규칙을 유지하고, 공개 범위 검증을 추가해 비공개 사용자의 활동이 노출되지 않도록 한다.

### 상태 관리 및 구조

- `ProfileVisibility` 모델과 표시 문구를 추가한다.
- `MyProfileDetailViewModel` 또는 전용 `ProfilePrivacyViewModel`: 현재 범위 로드·선택·저장·오류 상태를 관리한다.

## 5. 변경 확정 사항

- 체중 기반 칼로리 계산을 유지하기 위해 키·몸무게 입력·저장·검증은 제거하지 않는다.
- 프로필 편집의 다크 모드 개선은 유지한다.
- 공개 범위 조회는 Callable Function과 Firestore 규칙에서 함께 검증한다.
- `FirestoreService`: 공개 범위 저장, 레거시 신체 정보 정리, 서버 조회 API 호출을 Repository 역할로 캡슐화한다.
- `MyProfileDetailView`와 `ProfileEditView`는 UI/입력 전달만 담당한다.

## 6. 완료 기준 (Acceptance Criteria)

- [ ] 내 프로필 우측 상단 설정 버튼에서 공개 설정 화면으로 이동한다.
- [ ] 세 공개 범위 중 하나를 선택·저장하면 재진입 후에도 유지된다.
- [ ] 전체 공개 사용자는 로그인 사용자의 검색·추천·프로필 조회 대상이 된다.
- [ ] 친구만 공개 사용자는 상호 친구에게만 노출·조회된다.
- [ ] 비공개 사용자는 다른 사용자의 검색·추천·프로필 조회에서 제외된다.
- [ ] 본인은 공개 범위와 무관하게 자신의 프로필을 정상 조회·편집한다.
- [x] 프로필 편집과 온보딩의 키·몸무게 입력 및 검증이 유지된다.
- [x] Firestore와 UserDefaults의 키·몸무게 저장을 유지해 체중 기반 칼로리 계산을 보장한다.
- [ ] 프로필 편집 입력 영역이 라이트·다크 모드 모두에서 자연스럽고 충분한 대비를 가진다.
- [ ] Firestore 규칙·Cloud Function 테스트와 두 계정 실기기 QA를 통과한다.

## 9. 기술 검토 및 주의 사항

- 공개 범위를 클라이언트 UI에서만 숨기면 Firestore 직접 요청으로 데이터가 노출될 수 있으므로, 서버·규칙에서 강제해야 한다.
- 친구만 공개와 비공개 사용자의 검색/추천은 Firestore 컬렉션 쿼리만으로 안전하게 구현하기 어렵다. 서버 측 권한 판별을 기본 구현으로 한다.
- 공개 범위 변경 시 기존 친구 문서에 복제된 닉네임·이미지가 남을 수 있으므로, 목록 노출 정책과 동기화/필터링 기준을 구현 전에 확정한다.
- 실기기 QA 완료 전에는 PR을 생성하지 않는다.

---

> **검토 요청 사항**: 비공개 상태일 때 기존 친구 목록에서도 사용자를 완전히 숨길지, 관계는 유지하되 프로필 진입만 막을지 최종 정책 확인이 필요합니다. 현재 계획은 **기존 친구 관계는 유지하고, 검색·추천·프로필 조회는 모두 차단**하는 기준으로 작성했습니다.
